# Single-Registry Surface: UI on the OAuth API

**Status:** Draft for review
**Date:** 2026-08-16
**Builds on:** the MCP projection overhaul (landed on main 2026-08-16, commit `3865b64`)

## 1. Problem

The platform has one operation registry (`packages/capabilities`) and three consumers that should serve identical surfaces:

| Consumer | Wired to registry | State today |
| --- | --- | --- |
| OAuth API (`/api/v1`, external callers) | ✅ | Catch-all route dispatches from the registry |
| MCP (`/api/mcp`, agents) | ✅ | Projected from the registry (previous overhaul) |
| Next.js internal API (the dashboard's own endpoints) | ❌ | 144 standalone `route.ts` files with their own logic |

The internal routes are the remaining disease, and it is worse than a visibility gap:

- **Duplicated implementations.** The same operation exists twice — once as a capability `execute()`, once as a route handler body. They drift: different validation, different credit handling, different audit coverage. "Works in the UI but not the API" bugs are this design.
- **Features born dark.** New features start as internal routes (resonance runs, media jobs, insights, support assistant). Nothing forces them into the registry, so the OAuth API, the OpenAPI docs, and MCP never see them.
- **Docs structurally incomplete.** `openapi.json` is generated by iterating the registry. An endpoint that never enters the registry is undocumented forever; no scanner or annotation process can fix that.

## 2. Goal

**One implementation per operation, three doors.** Delete the internal API as a logic layer. The dashboard becomes a client of the same registry-served surface that external callers and agents use. End state property: *anything the UI can do is, by construction, in the OAuth API, the OpenAPI document, and the MCP tool list, with identical auth, credits, idempotency, and audit.*

For a product whose thesis is autonomous agents, this is a product property, not hygiene: every feature ships 100% automatable on day one.

## 3. Non-goals

- Replacing the home-built registry with an off-the-shelf contract router (oRPC/Hono). Evaluated and rejected: equivalent capability, minus the commercial middleware (credits, idempotency, audit, RLS) we already have.
- JSDoc/scanner-based documentation. Dead on arrival here: endpoints are registry entries, not files; there is nothing to scan. (Verified against the ecosystem — Next.js has no native docs story; all third-party options reduce to "structured definition somewhere," which we have.)
- Streaming tool results over MCP. The current MCP spec (2026-07-28) has no progressive tool output. Long-running work maps to the Tasks extension pattern, which our durable operations already match semantically.

## 4. Design

### 4.1 Consumer map (end state)

```
products/*  (repositories, orchestrators — logic lives ONLY here)
      ▲  called only from capability execute()/executeStream()
packages/capabilities  — unary + stream capability definitions
      │
      ├─→ /api/v1/[...path]     OAuth API: bearer tokens AND session cookies
      ├─→ /api/v1/openapi.json  docs (Swagger/Scalar)
      ├─→ /api/mcp              MCP projection (existing)
      └─→ (in-process)          SSR/server components call executeCapability directly
```

The internal API namespace (`/api/content/*`, `/api/outreach/*`, `/api/cascade/*`, …) is deleted.

### 4.2 Phase 1 — Session → context adapter

`/api/v1` currently authenticates only `Authorization: Bearer` via `getApiAuthorizationContext`. Extend it to accept the dashboard session:

- If a bearer token is present → existing OAuth path, unchanged.
- Else if a valid session cookie is present → mint the same `ExternalAuthorizationContext` from the session: organization from the active workspace, actor from the user, `role` from membership, and **scopes derived from role** (owner/admin ⇒ full scope set; narrower roles ⇒ their product scopes). `resource: "api"`.
- Cookie-authenticated **mutations require CSRF defense**: enforce `Origin`/`Sec-Fetch-Site` checks (extend the existing CORS/origin machinery) and rely on the session cookie's SameSite. Bearer requests are exempt (no ambient credential).

The token never lives in browser JS; the cookie stays httpOnly.

**Scope mapping is role-derived with one explicit exclusion:** `vn:commercial:operator` is never granted to a session context, regardless of role. It is a platform-operator scope, not a workspace-role scope; owner/admin sessions do not receive it. Operator capabilities remain reachable only through an OAuth token explicitly granted that scope (the `COMMERCIAL_OPERATOR_EMAILS` allowlist check inside `execute()` stays as the second gate).

**Session actor identity:** rate limiting and idempotency both key on `context.actor.clientId` (`packages/capabilities/rate-limit.ts`, `idempotency.ts`), and a session has no OAuth client. Session contexts use the synthetic client id **`session:<userId>`**: per-user rate buckets under a dashboard-specific policy (so external-client limits never throttle the UI, and one user's burst never throttles another), and a per-user idempotency namespace (two dashboard users replaying the same key never collide). Implementation must confirm the `oauth_client_id` columns on the rate-limit and idempotency tables carry no FK to `oauthClient`; if one exists, it is dropped in the same migration.

**Deliverable:** adapter in `packages/auth/server.ts` + `apps/unified/lib/external-api.ts`; tests: same capability call yields identical authorization decisions via bearer vs session for equivalent role/scopes; CSRF rejection tests; operator-scope exclusion test; rate-limit/idempotency isolation tests between two session users.

### 4.3 Phase 2 — Stream capabilities

Add a second contract to the registry for generative/progressive flows:

```ts
defineStreamCapability({
  id, version, risk, scopes, anyScopes, authorization, authorize,   // as unary
  input:  z.object({...}),
  chunk:  z.discriminatedUnion("type", [...]),  // typed progressive events
  output: z.object({...}),                      // final committed result
  rest:   { path, tag, summary, description },
  executeStream: async function* (context, input, execution) {
    // yields chunk; returns final output
  },
})
```

Projections per consumer:

- **UI:** `POST /api/v1/<path>/stream` → SSE. Chunks validated against `chunk`. Works with the AI SDK / generative-UI hooks (fetch-based streaming carries cookie or bearer auth; native `EventSource` is not used).
- **OAuth API:** buffered variant at the plain path — drains the stream, returns validated `output`. (Callers who want progress use the operation/task pattern instead.)
- **MCP:** tool returns the buffered final `output`. When the SDK supports the MCP Tasks extension, long-running stream capabilities map to task handles — thin adapter over the existing operation store, no redesign.
- **OpenAPI:** both representations documented (event-stream + buffered).
- **Cross-cutting:** credits reserved at start / settled at completion; one audit row at completion (status, duration); idempotent replay applies to the final output only.

**SSE protocol contract (normative):**

- Event types: `chunk` (validated against `chunk` schema), `result` (terminal; the validated final `output` — always the last event on success), `error` (terminal; `{code, message}` using capability error codes), plus periodic comment-line heartbeats to defeat idle proxies.
- Exactly one terminal event per stream: `result` or `error`, never both, never neither (a stream that ends without one is a server bug; the client treats silent close as `error: INTERNAL`).
- **Client disconnect:** the request's `AbortSignal` cancels `executeStream`; the credit reservation is settled for work actually performed (or released if none); the audit row records status `cancelled` with duration. Disconnect does not produce a committed result — no partial writes escape the orchestrator's own transaction boundaries.
- **Long streams:** the credit reservation lease is renewed on a fixed interval while the stream is live, so a legitimately long generation is never released mid-flight by reservation expiry; a failed renewal terminates the stream with `error: INSUFFICIENT_CREDITS`.
- **No resume:** streams are one-shot. A reconnect with the same idempotency key does not replay events; it hits the buffered path and returns the stored final output if the original run completed, or `CONFLICT` if it is still running.

**Deliverable:** registry support + the three projections + invariant tests (every stream capability has typed chunks, an output schema, and appears on all surfaces) + protocol tests for disconnect, error, and lease-renewal behavior.

### 4.4 Phase 3 — Migrate the 144 internal routes

Complete domain inventory (from `apps/unified/app/api`, excluding `v1`/`mcp`/`auth`):

| Domain | Includes | Notes |
| --- | --- | --- |
| content | drafts (+posts/publish/media/resonance), ideas (+draft/refine), projects (+ingest/entities), research (sources/items/run), topics (+generate/reset/restore), insights, channels, counts, generate-ideas | largest; many stream variants |
| content/media | jobs (+cancel), assets file download, fal webhook | file route + webhook are sanctioned exceptions |
| outreach | prospects deep tree (research/qualify/insights/evidence/intelligence/dossier/navigation/search/notes/activities/meetings/persona/account/outreach/qualification), accounts (+research/navigation/opportunities), personas, dimensions, action-items, catalog, settings/prompts | many stream variants |
| outreach webhooks | attendee/webhook, recall/webhook | sanctioned (signed inbound) |
| cascade | funnels (+emails/members) | |
| brain | overview, search, neighborhood | read-only queries; capabilities exist |
| chat | threads (+messages), chat stream | stream + thread CRUD |
| resonance | runs (+jobId) | job-handle pattern → operation capabilities |
| intelligence/v1 | token, runs, artifacts, workflows, attention | separately token-authenticated API — sanctioned as its own door, or folded into `/api/v1`; decide per route during migration |
| workspace | contacts (+outreach) | |
| commerce, admin, assistants/support | plans, credits, support tickets/history/escalate/feedback | |
| settings | developer-integrations | |
| uploads | `api/v1/uploads/[id]` companion route | binary; sanctioned |

Per domain, for each route:

1. **Capability exists and matches** → delete the route body; repoint the UI fetch to `/api/v1/...` (client) or `executeCapability` (SSR/server components). Delete the file.
2. **Capability missing** → author it (move the route's logic into `execute()`, exactly the MCP-cutover playbook), then step 1.
3. **Streaming route** → convert to a stream capability (Phase 2), UI switches to its SSE projection.
4. **Not an operation** → leave as a dedicated route, but it must be one of the sanctioned kinds (§4.6).

UI mutations adopt idempotency keys (generated client-side per action — free double-click protection). Each domain lands green on main independently; the dashboard keeps working throughout the migration.

Executed with parallel agents per domain, same verification bar as the MCP cutover: suite green, typecheck clean, surface invariants pass.

### 4.5 Phase 4 — Close the door (ratchet starts in Phase 1)

Architecture tests (in `tests/architecture/`):

- **Route allowlist as a ratchet — lands in Phase 1, not Phase 4.** The test enumerates every currently existing `route.ts` file path outside `/api/v1`, `/api/mcp`, `/api/auth` **by exact file path**. New files not on the list fail immediately — the internal API stops growing the day Phase 1 lands. As Phase 3 deletes routes, their entries are removed; the test also asserts the list only ever shrinks (an entry, once removed, cannot return). At Phase 4 completion the list contains only §4.6 sanctioned files, each annotated with its exception kind.
- **Import ban:** files under `apps/unified/app/api` may not import `products/*` repositories or orchestrators — domain access only via `@content-automation/capabilities`. (Mirror of the existing `mcp-projection-boundary` test.) Applied per-domain as each domain migrates.
- **Registry wiring:** every `catalog-*.ts` is registered in `registerPlatformCapabilities()` (kills the "defined but never wired" failure mode).

### 4.6 Sanctioned non-registry routes

Genuinely not operations; they keep dedicated files:

| Kind | Examples | Why |
| --- | --- | --- |
| Binary transfer | MCP media upload PUT (`api/v1/uploads/[id]`), media asset file download | streams bytes, one-time token auth |
| Inbound webhooks (signed) | fal webhook, outreach attendee/recall webhooks, delivery-provider callbacks | third-party initiated, signature verification instead of session/bearer |
| OAuth handshakes | publishing channel connect/callback | redirect dances |
| Auth/session | better-auth routes | the session system itself |
| Public unauthenticated | pricing/plan catalog surfaces intended for logged-out visitors | no principal to authorize; must stay cookie-free |
| Separately token-authenticated APIs | `intelligence/v1/*` (own bearer token minted at `intelligence/v1/token`) | distinct trust domain with its own token lifecycle; folded into `/api/v1` only if its auth model is unified first |

Streaming is **not** on this list — streams are registry citizens via Phase 2.

### 4.7 Documentation process (rides the same machinery)

- Every capability requires `rest.summary` + `rest.description`; every input field `.describe()`; no `z.unknown()` outputs without allow-list entry — enforced by a doc-coverage test.
- `openapi.json` checked in, regenerated by script, freshness verified in CI; `oasdiff` against main in PRs → automatic changelog + breaking-change gate.
- Optional: Scalar instead of Swagger UI; MCP prose overrides stay in `curation.ts`.

## 5. Risks and mitigations

- **Session-scope mapping errors** (role granted wrong scopes) → the adapter is one function with table-driven role→scope mapping; property tests assert bearer/session parity per role; the registry re-checks authorization on every call regardless of door.
- **CSRF regression** by accepting cookies on a formerly bearer-only surface → origin enforcement tested explicitly; mutations from disallowed origins rejected even with a valid cookie.
- **UI latency** (HTTP hop for what was an in-process call) → client fetches were already HTTP; SSR uses in-process `executeCapability`, so no self-fetch loops.
- **Behavior drift during migration** (capability differs subtly from the route it replaces) → migrate per domain with the domain's existing tests as the contract; divergences are surfaced and resolved in the capability, once.
- **Stream chunk vocabularies underspecified** → chunk schemas are required by the invariant test; the shared generative-UI hook already half-defines them.

## 6. What this kills, permanently

- API/docs/MCP lag: impossible (single source, three generated projections, drift = CI failure).
- Logic duplication between UI and API: impossible (route files with logic can't exist).
- Features invisible to automation: impossible (a feature that isn't a capability doesn't work in the UI either).

## 7. Execution order

1. Phase 1: session→context adapter **+ the route-allowlist ratchet** (freezes the internal API at 144 before anything else)
2. Phase 2: stream infra
3. Phase 3 domain by domain: content → outreach → cascade → brain/chat → resonance/intelligence/workspace → commerce/admin/support/settings
4. Phase 4: final enforcement (allowlist reduced to sanctioned exceptions, import ban repo-wide) + §4.7 doc process
